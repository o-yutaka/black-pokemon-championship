# Engineering Case Study: A Reliable Agent for a Strict External Engine

This repository is a domain-specific implementation of a broader engineering problem: how to connect a stateful decision agent to an external system whose currently exposed actions are the only legal source of truth.

## System boundary

The agent does not invent commands. For every decision, the engine supplies a selection contract containing:

- the current option array
- the minimum selection count
- the maximum selection count
- the state needed to interpret those options

The submission returns option indexes, not arbitrary action names. A semantically reasonable action is still invalid when it is absent from the current option array.

## Reliability requirements

The runtime must satisfy four independent contracts:

1. **Action legality** — every returned index is an integer, unique, in range, and within the current minimum/maximum count.
2. **Runtime safety** — policy exceptions, invalid output, or budget overruns must degrade to a deterministic legal fallback.
3. **Packaging integrity** — the built archive must contain exactly the reviewed entrypoint, deck, engine files, and required external-engine bindings.
4. **Evidence integrity** — fast screens may detect crashes and regressions, but are not presented as official performance or promotion evidence.

## Implemented architecture

```text
Legal selection validator ---- invalid / timeout / exception
        |                                  |

        |                                  |
        +------------------+---------------+
                           v

                           |
                           v
              decision overlay + truth ledger
```

### Runtime enforcement

`black_engine/runtime.py` implements the final execution boundary.

- `legalize_selection()` validates type, uniqueness, cardinality, and index range.
- `deterministic_fallback()` derives a legal result only from the current selection contract.
- `SubmissionRuntime.decide()` measures elapsed time, catches policy failures, and records whether the result came from the policy or fallback.
- `_capture_overlay()` preserves runtime source, chosen indexes, warnings, and error information for later diagnosis.

The policy is therefore not trusted merely because it returned a list. Its output must pass the same external contract every time.

### Exact submission contract

`submission_contract.py` defines the canonical source tree and archive file order.

It verifies:

- required root files
- required `black_engine/` files
- required `cg/` engine bindings
- non-empty native engine library
- valid 60-card deck and required ACE-spec constraint
- absence of alternate runtime routers or extra archive files

The reviewed `main.py` and `deck.csv` are copied into the final bundle rather than regenerated by an opaque pipeline.

### Static and isolated execution gate

`scripts/static_gate.py` validates assumptions that ordinary unit tests can miss.

- Parses `main.py` with `ast`.
- Rejects direct `__file__` access because the hosted runner may execute source through raw `exec()` without normal module globals.
- Rejects environment-specific absolute paths.
- Builds and extracts the archive in a temporary directory.
- Executes the extracted entrypoint in isolated Python mode.
- Verifies the deck handshake and a normal selection response.

This tests the artifact that will run, not only the source tree that produced it.

## Policy layer

`black_engine/policy.py` translates current engine state into deterministic option scores. It handles card selection, energy placement, evolution, abilities, attacks, switching, target selection, and resource-sensitive routes.

The important architectural boundary is that policy scoring never bypasses runtime legality. Strategy may evolve while the execution contract remains fixed.

## Evaluation discipline

`scripts/fast_eval.py` is intentionally described as a crash, speed, and regression screen.

That distinction prevents a common evaluation failure: treating a convenient local opponent, deterministic baseline, or small sample as proof of universal strength. Promotion claims require separate evidence and remain outside this fast screen.

## Transfer to business AI agents

| Strict-engine agent | Business AI system |
|---|---|
| Engine-provided option array | Tool/API allow-list for the current workflow state |
| Minimum and maximum selection count | Required/optional request fields and action cardinality |
| Option-index execution | Versioned external action identifier |
| Hidden-state discipline | Evidence and observation boundary |
| Invalid selection rejection | Schema, authorization, and contract validation |
| Deterministic fallback | Safe degraded operation |
| Runtime decision overlay | Audit trace and observability context |
| Exact submission archive | Reproducible deployment artifact |
| Crash/regression screen | Pre-production evaluation gate |

The same principles are applied to a business workflow in [`o-yutaka/AI-AI`](https://github.com/o-yutaka/AI-AI), where engine options become allowed external actions, high-impact operations require approval, idempotency prevents duplicate side effects, and decision traces are stored durably.

## Reviewer path

1. `black_engine/runtime.py` — final legality and failure boundary
2. `submission_contract.py` — canonical artifact contract
3. `scripts/static_gate.py` — isolated deployment-artifact verification
4. `black_engine/policy.py` — deterministic domain policy
5. `scripts/build_submission.py` — reproducible package builder
6. `scripts/fast_eval.py` — bounded screening harness

## Reproduce the gates

```bash
python scripts/static_gate.py
python -m pytest -q
python scripts/build_submission.py \
  --cg-dir /path/to/official/cg \
  --out artifacts/submission.zip
```

A complete runtime evaluation additionally requires the official external engine bindings, which are not replaced by a custom simulator in this repository.

## Claim boundary

This repository demonstrates strict external-action contracts, deterministic policy execution, packaging integrity, runtime fallback, and evaluation discipline.

It does not claim that a game-specific heuristic policy is a general-purpose planner, that a local fast screen is official leaderboard evidence, or that external engine binaries can be reproduced from the public Python source alone.
