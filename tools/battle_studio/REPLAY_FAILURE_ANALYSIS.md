# BLACK Replay Failure Analysis v1

## 目的

Kaggle公式形式のリプレイから観測可能な失敗シグナルを抽出し、デッキまたはPolicyの変更仮説へ接続する。UIは敗因を断定せず、必ず元フレーム、観測事実、限界、検証方法を残す。

## Fail-closed条件

敗因抽出は次のどちらかで勝者を一意に確認できた場合だけ実行する。

1. 終局フレームの`result`に明示的なWinnerがある
2. 片方だけサイドが0枚である

以下は集計しない。

- 対戦途中
- Winnerを安全に解釈できない結果文字列
- 勝利リプレイ
- 結果不明リプレイ

現在の自分側はP1、`subjectPlayer=0`として扱う。相手側を分析するための自動反転は行わない。

## 分類コード

| Code | 観測条件 | 断定しないこと |
|---|---|---|
| `SETUP_LOW_BOARD` | ターン2までの最大盤面・ベンチが少ない | たね枚数不足とは断定しない |
| `ENERGY_DEVELOPMENT_MISS` | ターン2まで場のエネルギーが0枚 | デッキ内エネルギー不足とは断定しない |
| `ATTACK_DELAY` | 攻撃が未観測、または初回攻撃がターン3以降 | イベント欠落とPolicy問題を区別せず断定しない |
| `HAND_STALL` | ターン4まで手札2枚以下が複数の自分行動フレームで続く | ドロー不足とは断定しない |
| `BENCH_COLLAPSE` | 終局時にベンチ0、盤面1体以下 | 最終KO直後の一時状態を除外できない |
| `DECK_EXHAUSTION` | 終局時の山札が2枚以下 | 過剰ドローか長期戦設計かは断定しない |
| `PRIZE_RACE_BEHIND` | 終局時のサイド差が3枚以上 | カード変更だけで解決するとは断定しない |
| `HIGH_DISCARD_LOAD` | トラッシュ10枚以上かつ回収イベント未検出 | 回収札不足とは断定しない |

出力契約は`schemas/replay-failure.schema.json`。

## 変更候補

候補は常に`status=unverified`。UI側で勝率改善値を作らない。

### デッキ候補

- 主軸たねポケモン +1
- たね展開札 +1
- 既存エネルギー +1
- ドロー・手札更新札 +1
- 回収・復帰札 +1

候補カードはカードDBの名称・効果と現在の60枚から抽出する。60枚を超えるため、削るカードは自動決定しない。候補ボタンはカード検索へ送るだけで、`deck.csv`を勝手に変更しない。

### Policy候補

- 山札保護Policy
- サイド経路・攻撃対象Policy

Policy候補はデッキ変更と分離する。同一デッキ・同一EngineでPolicyだけを変えたBundleを公式形式で評価する。

## 履歴

終局したリプレイを`replayId`で重複排除し、ブラウザの`black.replayFailureHistory.v1`へ最大100試合保存する。途中リプレイは保存しない。UIの「履歴を消去」で削除できる。

## 証拠表示

各Findingは次を持つ。

- `frameId`
- `turn`
- `actionCount`
- 観測要約
- 生の盤面事実
- 信頼度
- 分類の限界

現在開いているリプレイの証拠ボタンを押すと、そのフレームへ移動する。過去履歴のリプレイ本体は保存しないため、過去試合のフレームへ移動するには元JSONを再度開く必要がある。

## 昇格条件

生成候補は提出候補ではない。次の流れを守る。

1. 未検証候補をCurrentから分岐
2. Deck / Policy / Engine / Bundle SHAを固定
3. Kaggle公式形式だけで先後攻を揃えて評価
4. 対面別勝率、初動、攻撃開始ターン、Engine error、timeoutを比較
5. `deck-analysis.json`へ実測結果を記録
6. Bundle Gate全緑で初めて提出候補へ昇格
